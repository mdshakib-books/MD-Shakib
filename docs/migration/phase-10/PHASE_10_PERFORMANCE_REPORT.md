## 3. CORE WEB VITALS & ARCHITECTURAL OPTIMIZATIONS

### 3.1 Largest Contentful Paint (LCP) Optimization
- **The Bottleneck:** The homepage hero presentation previously set a 3540px Unsplash image via inline CSS `style={{ backgroundImage: url(...) }}` on a generic `div`. As an inline CSS background, the browser's preload scanner could not discover the image until DOM and CSSOM trees were constructed. Furthermore, Next.js could not optimize, resize, or convert the asset to modern formats.
- **The Solution:**
  - Replaced CSS background image with Next.js `<Image />` component.
  - Specified `priority`, `fill`, and responsive `sizes="(max-width: 768px) 100vw, (max-width: 1200px) 100vw, 1440px"`.
  - Configured Next.js image optimization pipeline with AVIF and WebP format generation.
  - Added `fetchpriority="high"` automatically generated by Next.js.
- **Result:** Desktop LCP plummeted from **2.6s** to **0.9s**, an empirical improvement of 1.7 seconds.

### 3.2 Font Loading & Render-Blocking Elimination
- **The Bottleneck:** In `apps/web/app/globals.css`, Line 1 imported Google Fonts synchronously:
  `@import url("https://fonts.googleapis.com/css2?family=Cinzel:...&family=Inter:...&display=swap");`
  Lighthouse flagged a **417 ms wasted delay** blocking initial page rendering while waiting for remote Google Fonts CSS and WOFF2 files.
- **The Solution:**
  - Removed the external CSS `@import` entirely.
  - Configured `Cinzel` and `Inter` via `next/font/google` in `apps/web/app/layout.tsx`.
  - Injected CSS variables `--font-cinzel` and `--font-inter` into `<html>`.
  - Set `display: "swap"` and Latin subsets.
  - Next.js automatically self-hosts font binaries at build time, eliminating external third-party requests and preloading `@font-face` definitions directly in document `<head>`.
- **Result:** Wasted render-blocking request time dropped from **417 ms** to **0 ms**. FCP dropped from **0.7s** to **0.3s**.

### 3.3 Product Image Optimization & Sizing
- **The Bottleneck:** Product cards on the storefront (`BookCard.tsx`), detail pages (`BookDetailClient.tsx`), and cart (`CartClient.tsx`) previously rendered raw HTML `<img>` tags. An uncompressed 600x900px asset was delivered into a 189x283px container, wasting ~140 KiB of network bandwidth across catalog views.
- **The Solution:**
  - Converted `BookCard.tsx`, `BookDetailClient.tsx`, `CartClient.tsx`, and `OrderDetailClient.tsx` to Next.js `<Image />`.
  - Configured aspect-ratio preserving container with `fill` and accurate `sizes` attributes:
    `sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 25vw"`
  - Whitelisted remote domains in `next.config.ts`: `res.cloudinary.com`, `images.unsplash.com`, `plus.unsplash.com`.
  - Enabled modern compression formats: `formats: ["image/avif", "image/webp"]`.
- **Result:** Zero CLS layout shift (`0.000`), automatic AVIF/WebP compression, and crisp high-DPI scaling across all viewports.

## 4. JAVASCRIPT BUNDLE & SERVER RENDERING AUDIT

### 4.1 Production Bundle Composition
- **Total Production JS Chunks:** 48 code-split chunks.
- **Average Chunk Size:** **33 KiB** (well within Next.js recommended < 100 KiB per chunk limit).
- **Zero Monolithic Bundles:** All route modules are split at page and layout boundaries.
- **Client JS on Homepage:** Under **180 KiB** total transferred JS for full hydration, including React 19 runtime, Lucide icons, motion reveal client component, and cart context provider.

### 4.2 Rendering Strategy Alignment
- **Server Components by Default:** Catalog data fetching (`getBooks`, `getBookById`, `getFeaturedBooks`), layout shell (`Navbar`, `Footer`, `HeroSection`), legal pages, and order details load on the server without client bundle weight.
- **Client Components Strictly Isolated:** Client interactivity is restricted to `BookCard` (add-to-cart click handler), `SearchBar` (combobox focus), `ScrollReveal` (intersection observer), and interactive modals.
- **ISR Caching:** Homepage uses `export const revalidate = 60`, providing instant static cache responses with background revalidation.
- **Dynamic User Route Isolation:** Sensitive routes (`/account/*`, `/orders/*`, `/checkout`) use `export const dynamic = "force-dynamic"`, guaranteeing that no personalized customer data is ever cached at the edge or served to other customers.
